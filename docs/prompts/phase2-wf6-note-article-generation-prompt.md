
# Phase2 WF6: note記事自動生成 実装プロンプト（実現性重視版）

**作成日**: 2025-01-12  
**対象ワークフロー**: WF6 - note記事自動生成  
**カテゴリー**: 新規ワークフロー作成（AIコンテンツ生成）  
**優先度**: P0（高）  
**工数見積**: 30🍅（10ユニット）  
**依存関係**: WF5完了後に実装

---

## 改訂趣旨

- noteには公開された公式APIが存在せず、自動投稿までをノーコードで安定運用するのは現実的に難しい。  
- Phase2では「AIによる高品質な下書き生成と人手での最終投稿」に軸足を置き、後続の自動化はオプション扱いとする。  
- 生成系AI・Notion API・Slack通知など既存の安定したAPI群を活用し、短期間でのPoC→本番運用を目指す。  
- Playwright等のブラウザ制御は拡張オプションとして切り出し、導入判断を後回しにできる構成にする。

---

## 実装用プロンプト

```markdown
@mcp-sequential-thinking
@n8n-workflows-docs
@n8n-mcp

Phase2のWF6（note記事自動生成）の実装準備を進めたいです。以下の前提とゴールを守りつつ、段階的に設計・構築してください。

【背景・現状】
- WF5でトピックマスタDBに人気トピックが週2回更新される。
- 手動で記事を書くと1本2-3時間かかり、週10本のペースを維持できない。
- noteには公式APIがなく、自動投稿は技術的にも運用的にもハイリスク。
- Phase1で構築したnote記事管理DB（29968d5c-2986-81ad-90d0-c24ed710503e）を活用する。
- 目標: AIが「公開可能レベルの下書き」を安定供給し、週10本の公開体制を人手連携で確立する。

【今回のゴール】
- トピックマスタを参照 → GPTで下書きを生成 → Notion DBに保存 → Slackでレビュー依頼を通知、までを完全自動化。
- Playwright等によるnote投稿自動化はオプションとして検討に留める（導入判断は別タスク）。

【トリガー】
- Schedule: 毎日 09:00 JST（営業時間内に確認できるよう1時間前倒し）
- 任意実行用のManual Triggerを残す（急ぎで本数を追加したい場合を想定）

【入力データ】
- ソース: Notion トピックマスタDB（{{TOPIC_MASTER_DB_ID}}）
- フィルター条件: Status = "active", Last Generated < 今日, Priority フラグを考慮
- ソート: Score DESC → Score同値はExtracted At ASC
- 取得プロパティ: Topic Name, Score, Keywords（配列）, Related Articles, Extracted At, Notes（補足）

【処理フロー（12ノード構成）】
1. **Schedule Trigger**  
   - Cron: Daily 09:00 JST  
   - Manual triggerノードを並列に配置

2. **HTTP Request: トピック取得**  
   - Notion `/v1/databases/{{TOPIC_MASTER_DB_ID}}/query`  
   - ページサイズ: 5件  
   - リトライ: 3回 / Exponential backoff

3. **Function: トピック選定**  
   - 重複投稿防止のため、過去7日以内に使用済みのtopicIdは除外  
   - 最終的に1件のみ採用し、未決定の場合はSlackに「ネタ切れ」を通知して終了

4. **HTTP Request: GPT-4タイトルアイデア生成**  
   - model: `gpt-4.1-mini`（コストと安定性のバランス）  
   - 3パターン（How-to / 疑問形 / ストーリー）をJSONで返却  
   - temperature: 0.7, max_output_tokens: 800

5. **Function: タイトルスコアリング**  
   - CTR優先度: How-to > 疑問形 > ストーリー  
   - クリック想定ワード（例: 入門, 具体例, 3つのコツ 等）の有無で+1補正  
   - 選定理由をメモとして保存

6. **HTTP Request: GPT-4構成案生成**  
   - model: `gpt-4.1-mini`  
   - タイトル・キーワード・関連既存記事を渡し、見出し案と要点を箇条書きで生成  
   - 文字数の目安: 約2,400字（noteでの読みやすさと実行時間のバランス）

7. **HTTP Request: GPT-4本文生成**  
   - model: `gpt-4.1`  
   - system promptでターゲット（3-10歳児の保護者）とトーンを明示  
   - 入力: タイトル / トピック概要 / キーワード / 構成案  
   - 出力: note準拠Markdown、2,000〜2,600文字  
   - temperature: 0.65, max_output_tokens: 3600  
   - 安全性: OpenAIの`reasoning: false`, `presence_penalty: 0.1`

8. **Function: 品質チェック**  
   - 文字数・見出し数・禁止ワード（例: 「無料で」「絶対に」など過剰表現）を検査  
   - 条件を満たさない場合は再生成（最大1回）→ それでも不合格ならSlackへレビュー依頼して終了

9. **Function: Notion登録用データ整形**  
   - categories: keywords上位3件  
   - preview: 冒頭400文字を抽出  
   - metadata: {topicId, generatedAt, model, retryCount, titleCandidates, outline}

10. **HTTP Request: Notion記事管理DB登録**  
    - Database ID: 29968d5c-2986-81ad-90d0-c24ed710503e  
    - 必須プロパティ:  
      - Title = 選定タイトル  
      - Status = "要レビュー"（手動で公開済み→"公開済み"に更新）  
      - Generated By = "AI"  
      - Article Draft（Rich text）= 本文Markdown  
      - Topic ID, Score, Outline, Metadata（JSON形式）を別プロパティで保持

11. **HTTP Request: Slack通知**  
    - Webhook先: #新規記事  
    - 内容: タイトル / トピック / 想定文字数 / レビュー締切 / NotionページURL  
    - Playwright自動投稿オプションが未有効の場合は、その旨テンプレートで明記

12. **Function: 実行結果ログ整形**  
    - 成功・失敗をJSON化してn8nのExecution logへ記録  
    - エラー時はNotionに失敗ログを残す（任意のログDBを想定）

【拡張オプション（別タスク扱い）】
- Playwright MCP経由でnoteへ下書きアップロード  
  - 前提: 専用のブラウザワーカー環境・2段階認証対応・CSRFトークン監視  
  - MVPでは導入しない。WF6の安定運用が確認できた後、WF6.1として検討する。

【エラーハンドリング】
- Notion API: 429/5xxで最大3回リトライ。失敗時はSlackに「トピック取得失敗」通知。
- GPT-4 API: タイトルと本文で個別のリトライカウンタ（2回）。同一トピックで連続失敗したら手動レビューへ渡す。
- 品質チェックNG: 記事はNotionに「下書き要修正」ステータスで保存し、Slackに要対応通知。
- Slack送信失敗: ローカルJSONに退避（n8nの`Write Binary File`）し、別途確認できるようにする。

【活用サービス】
- Notion API（bearer token: `YOUR_NOTION_API_TOKEN`）
- OpenAI API（`gpt-4.1` / `gpt-4.1-mini`）
- Slack Incoming Webhook
- n8n標準ノード + Functionノード（TypeScript）

【使用禁止・注意】
- note非公式APIやCookie再利用による直接投稿は行わない。
- Google Sheetsは使用しない（Phase1で廃止済み）。
- Playwrightを使う場合も、必ずステージング環境で検証し、CSRF対策とログイン情報の安全管理を徹底する。

【KPI / モニタリング】
- 下書き生成成功率: ≧90%（品質チェック合格が目標）
- 人手レビュー完了までの平均リードタイム: 24時間以内
- 1実行あたりのOpenAIトークン消費量: タイトル+構成+本文で合計 ≦ 6,000 tokens
- 実行時間: 6分以内（GPTレスポンス待ち含む）

【想定される調査タスク】
1. Notion DBのプロパティ名を再確認し、必要なIDを環境変数化。  
2. 既存のGPTプロンプト資産（WF4/Phase1）から転用可能なテンプレを洗い出す。  
3. Slackメッセージのフォーマットをチームで合意しておく（レビュー期限や担当アサイン方法）。  
4. Playwright導入検証の是非を判断するため、noteのログイン手順・CSRF挙動を調査（別チケット）。  
```

## 実装後の検証項目

### 機能検証
- [ ] Schedule Triggerが日本時間09:00に起動する。
- [ ] トピックマスタから未使用トピックを取得できる。
- [ ] GPT-4.1-miniがタイトル案を3件返却し、スコアリングが想定通り動く。
- [ ] GPT-4.1が2,000〜2,600文字の本文を生成する。
- [ ] Notion記事管理DBに`Status = "要レビュー"`でページが追加される。
- [ ] Slack通知のテンプレートが期待どおりに整形される。

### コンテンツ品質検証
- [ ] タイトルが30文字以内・ターゲット読者に刺さる表現になっている。
- [ ] 本文が導入→本論→まとめの構成で、見出しが適切に配置されている。
- [ ] 禁止ワードフィルタが正しく動作している。
- [ ] keywords上位3件がカテゴリとして設定され、Notionでのフィルタリングに使える。

### エラーハンドリング検証
- [ ] Notion/GPT/Slackそれぞれでリトライ回数・Slack通知が期待通りに機能する。
- [ ] 品質チェックNG時に再生成→失敗で要修正フローへ切り替わる。
- [ ] 失敗ログがNotionまたはn8nのExecution logで追跡できる。

### パフォーマンス検証
- [ ] 1実行の所要時間が6分以内。
- [ ] OpenAIトークン使用量が1日あたり ≦ 60,000 tokens（10本想定）。
- [ ] Notion APIへのリクエストがレート制限（3req/sec）内に収まっている。

### データ整合性検証
- [ ] Article Draftフィールドに本文全文が入っている。
- [ ] MetadataにトピックID・モデル名・生成日時が記録される。
- [ ] Generated Byが常に"AI"で登録され、人手記事と区別できる。
- [ ] 同一トピックで複数の未公開記事が残らない（トピック選定ロジックが機能）。

## note投稿オプションの取り扱い

- **現状の結論**: note公式APIが無いため、公開までの全自動化は保守性・規約順守の観点で採用しない。  
- **暫定運用**: Notionで「要レビュー」→ 人手でnoteにコピペ → 公開後にNotionで`Status = "公開済み"`へ更新。  
- **追加開発候補**:  
  1. Playwright MCPでブラウザ自動操作（2段階認証・Captcha対応が前提）  
  2. noteの「外部連携（β）」やZapier対応が公開された場合に備えて監視  
  3. 別途Chrome拡張を社内利用で作成（要セキュリティ審査）

## 次のステップ

1. WF6ワークフローの試験実行（トピック1件）でNotion下書きとSlack通知を確認。  
2. レビューフロー（Notion→Slack→公開→ステータス更新）をチームで標準化。  
3. 生成品質に関するフィードバックを収集し、GPTプロンプトを調整。  
4. Playwright等の自動投稿が必要かどうか、定量的に判断する材料（レビュー負荷・ヒューマンエラー率）を集める。
