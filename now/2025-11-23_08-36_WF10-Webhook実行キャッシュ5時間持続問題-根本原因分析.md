# WF10 Webhook実行キャッシュ5時間持続問題 - 根本原因分析レポート

**作成日時**: 2025-11-23 08:36:12 JST

## 📋 問題概要

**問題**: WF10-Main Webhookワークフローにおいて、Share File nodeの設定を修正してもn8n実行コンテキストが古い定義を使用し続け、5時間以上経過しても更新されない。

**影響範囲**:
- ✅ ワークフロー定義（JSON）：正しい設定が保存されている
- ❌ Webhook実行コンテキスト：古い設定（`permissionsUi: {}`）を使用し続ける
- 🎯 結果：Google Drive Share File APIが400エラー（"permission type field is required"）で失敗

## 🧪 実験結果

### 実験1: 通常のワークフロー更新（v17）
- **方法**: `n8n_update_partial_workflow`でShare File nodeパラメータ修正
- **期待**: 次回実行で新しい設定を使用
- **結果**: ❌ 19秒後の実行でも古い設定（`permissionsUi: {}`）を使用
- **結論**: 通常の更新では即座にキャッシュクリアされない

### 実験2: 3分間待機後のテスト（v19）
- **方法**: v19更新後、3分間待機してから実行
- **期待**: 時間経過でキャッシュがクリアされる
- **結果**: ❌ 14分11秒後の実行でも古い設定を使用
- **結論**: 短時間の待機ではキャッシュクリアされない

### 実験3: 完全ワークフロー更新（v21）
- **方法**: `n8n_update_full_workflow`で全ノード・全接続を含む完全更新
- **期待**: 構造的変更でキャッシュが強制クリアされる
- **結果**: ❌ **5時間8分34秒後**の実行でも古い設定を使用
- **結論**: 完全更新でもキャッシュは一切クリアされない

### 実験4: ワークフロー再アクティブ化試行
- **方法**: `active: false`設定でワークフローを非アクティブ化
- **期待**: 非アクティブ化→再アクティブ化でキャッシュクリア
- **結果**: ❌ n8n APIが`active: false`を無視し、`active: true`のまま維持
- **結論**: Webhook型ワークフローはAPI経由での非アクティブ化不可

## 🔬 根本原因分析

### アーキテクチャ推定

```
┌─────────────────────────────────────┐
│  n8n Workflow Storage (Database)    │  ← 定義はここに保存（正しい設定）
│  - ワークフロー定義 (v17/v19/v21)   │
│  - nodes, connections, settings      │
└─────────────────────────────────────┘
              ↓ 読み込み（初回のみ）
┌─────────────────────────────────────┐
│  Webhook Execution Context Cache    │  ← 実行時はここから読み込み
│  - 初回起動時にワークフロー定義を    │
│    メモリにロード                     │
│  - 以降はメモリ上の定義を使用         │
│  - 定義更新イベントを監視しない       │
└─────────────────────────────────────┘
              ↓ 実行時に使用
┌─────────────────────────────────────┐
│  Webhook Request Handler             │
│  - キャッシュされた古い定義で実行    │
│  - Share File: permissionsUi: {}     │
└─────────────────────────────────────┘
```

### 根本原因の特定

**原因1: Webhook実行コンテキストの独立性**
- Webhook経由の実行は独自のキャッシュ層（おそらくメモリ内）を使用
- ワークフロー定義の更新イベントがこのキャッシュ層に伝播しない

**原因2: キャッシュ更新トリガーの欠如**
- n8n APIの`update_workflow`操作は定義を保存するが、実行コンテキストキャッシュをクリアしない
- Railway環境ではキャッシュクリアのメカニズムが機能していない可能性

**原因3: Webhook型ワークフローの特殊性**
- 通常のワークフロー：実行開始時に最新定義を読み込む
- Webhook型ワークフロー：サーバー起動時に定義をメモリにロードし、以降は再読み込みしない

## 📚 学習ポイント

### n8n Railway環境の制約

1. **Webhookワークフロー実行キャッシュは永続的**
   - 定義更新後も古い設定を使用し続ける
   - 5時間以上経過してもキャッシュがクリアされない

2. **API経由の更新は実行コンテキストに反映されない**
   - `n8n_update_partial_workflow`: 定義のみ更新
   - `n8n_update_full_workflow`: 定義のみ更新
   - いずれもWebhook実行キャッシュをクリアしない

3. **Webhook型ワークフローの非アクティブ化制約**
   - API経由で`active: false`設定は無視される
   - UI経由でも同様の可能性が高い
