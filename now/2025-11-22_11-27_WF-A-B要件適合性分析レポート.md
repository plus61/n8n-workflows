### 3. OpenAI API認証の二重化リスク

#### 現状の実装
**WF-A - OpenAI - Generate Note Draft**:
```javascript
"Authorization": "={{ 'Bearer ' + $env.OPENAI_API_KEY }}"
```
- ⚠️ 環境変数参照 (`$env.OPENAI_API_KEY`)
- ⚠️ n8n Credentials登録も併用 (id: `aWGOKXo23vBQe9xs`)

#### 設計仕様書§10の要件
> APIキー: n8n Credentialsに保存（**環境変数渡し禁止**）

**問題点**:
1. 環境変数が未設定の場合、認証エラー発生
2. Credentialsとの二重管理によるセキュリティリスク
3. 設計仕様書の明示的な禁止事項に違反

**影響**: 本番環境で環境変数が設定されていない場合、API呼び出し失敗

**推奨対応**:
```javascript
// HTTP Requestノードの認証設定
authentication: "predefinedCredentialType"
nodeCredentialType: "openAiApi"

// Headerから Authorization を削除
// n8n Credentialsが自動的にAuthorizationヘッダーを追加
```

### 6. JSONパースのエラーハンドリング不足

#### 現状の実装
**WF-A - Parse OpenAI Note JSON**:
```javascript
try {
  parsed = JSON.parse(content);
} catch (e) {
  parsed = {
    title: 'タイトル生成エラー',
    body: content,
    segment: $json.segment || $json.default_segment || 'Cold',
  };
}
```

**問題点**:
- ✅ 基本的なtry-catchは実装済み

**影響**: OpenAIのJSON生成失敗に気づかず、不正なデータがSheetsに書き込まれる

**推奨対応**:
1. catchブロック内でSlack通知ノードへ分岐
2. エラー情報（元のプロンプト、OpenAI応答、エラー内容）を通知
3. エラー行には `status=error` などの専用フラグを設定

### 7. OpenAI応答スキーマの検証不足

#### 設計仕様書§4-2で要求されるJSONスキーマ
```json
{
  "generated_title": "string",
  "generated_body": "markdown string",
  "segment": "Cold|Middle|Hot|Current",
  "keyword_used": "string",
  "reasoning": "string"
}
```

#### 現状のFunctionノード
```javascript
parsed = JSON.parse(content);
// → そのまま使用（検証なし）
```

**問題点**:
- ❌ 必須キー（`keyword_used`, `reasoning`）の存在チェックがない
- ❌ `segment`のenum検証がない (Cold/Middle/Hot/Current以外を許容)
- ❌ OpenAIが意図しない形式で返した場合のフォールバック未実装

**影響**: データ整合性が保証されず、後続処理でエラー発生の可能性

**推奨対応**:
```javascript
// スキーマ検証ロジック追加
const requiredKeys = ['title', 'body', 'segment'];
const validSegments = ['Cold', 'Middle', 'Hot', 'Current'];

for (const key of requiredKeys) {
  if (!parsed[key]) {
    // Slackエラー通知 + デフォルト値設定
  }
}

if (!validSegments.includes(parsed.segment)) {
  parsed.segment = $json.segment || 'Cold'; // フォールバック
}
```
