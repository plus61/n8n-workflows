# WF10 Webhook実行キャッシュ問題 - Railway n8n再デプロイ手順書

**作成日時**: 2025-11-23 08:44:50 JST

## 📋 問題概要

**問題**: WF10-Main Webhookワークフローの実行コンテキストキャッシュが5時間以上持続し、Share File nodeが古い設定（`permissionsUi: {}`）を使用し続けている。

**根本原因**: Webhook実行コンテキストがプロセスレベルでメモリキャッシュされ、ワークフロー定義の更新では無効化されない。

**解決策**: Railway n8nサービスの再デプロイ（プロセス再起動）によるキャッシュクリア。

詳細は `2025-11-23_08-36_WF10-Webhook実行キャッシュ5時間持続問題-根本原因分析.md` を参照。

## 🚀 Railway Web UIからの再デプロイ手順

### ステップ1: Railway Dashboardにアクセス

```bash
# ブラウザでRailway Dashboardを開く
railway open
```

または直接URLでアクセス:
- URL: https://railway.app/dashboard
- プロジェクト: n8n-python-production

### ステップ2: n8nサービスを選択

1. **プロジェクト一覧** から `n8n-python-production` を選択
2. **サービス一覧** から `n8n` サービスを選択
3. **Deployments** タブをクリック

### ステップ3: 最新デプロイメントを再デプロイ

1. **最新のデプロイメント**（一番上の行）を確認
2. デプロイメント行の右端にある **「⋮」（3点メニュー）** をクリック
3. ドロップダウンメニューから **「Redeploy」** を選択
4. 確認ダイアログで **「Redeploy」** ボタンをクリック

### ステップ4: 再デプロイ完了を待機

**予想所要時間**: 約1〜3分

**進行状況の確認**:
- **Building**: イメージビルド中（約30秒〜1分）
- **Deploying**: デプロイ中（約30秒）
- **Active**: デプロイ完了・サービス稼働中（✅ 緑色のステータス）

**ログ確認**（オプション）:
```bash
# CLI経由でリアルタイムログを確認
railway logs
```

### ステップ5: ヘルスチェック（30秒待機後）

再デプロイ完了から約30秒待機してから、以下を実行:

```bash
# n8n Webhookエンドポイントの疎通確認
curl -I https://n8n-python-production-344b.up.railway.app/webhook/wf10-notion-trigger
```

**期待される出力**:
```
HTTP/2 200
```

### 2. 技術的知見のドキュメント化

今回の問題から得られた重要な知見:

1. **n8n Webhook実行コンテキストの特性**:
   - プロセスレベルでメモリキャッシュされる
   - ワークフロー定義更新では無効化されない
   - Railway再デプロイ（プロセス再起動）が必要

2. **Phase 0検証の重要性**（再確認）:
   - Railway環境での実行テストは必須
   - ノード設定の完全性確認（全パラメータ）
   - エラーハンドリング検証

3. **今後の運用ベストプラクティス**:
   - Webhook型ワークフローの設定変更後は必ず再デプロイ
   - 重要なノード（Share File等）は初回実行で即座に確認
   - 問題発見時は即座にRailway再デプロイ
